# BACKLOG

Задачи, отложенные по просьбе владельца. Формат: проблема → ожидаемое поведение → критерий готовности.

## UX: создание задачи блокирует интерфейс

**Проблема (2026-11-11).** В Mini App после нажатия «Создать» интерфейс блокируется на всё время генерации плана: `CreateTask` синхронно ждёт ответ STRATA (десятки секунд), кнопка/форма недоступны, прогресса нет. Пользователь видит только «выполняется» уже после создания.

**Ожидаемое поведение.**
- `POST /api/tasks` отвечает быстро: задача создаётся в статусе `planning`, план генерируется фоновой горутиной/воркером.
- UI сразу показывает карточку «План готовится…» с возможностью отменить; форма разблокирована.
- Ошибка планирования переводит задачу в `failed` с понятной причиной и кнопкой «Повторить план», а не молчаливый таймаут.
- Telegram `/task` получает тот же асинхронный путь (не блокирует dispatcher на минуту).

**Критерий готовности.**
- p95 ответа `POST /api/tasks` < 300 мс при живом STRATA.
- UI не блокируется, виден статус `planning` и отмена.
- Тест: медленный fake-модельный клиент (5 с) не задерживает HTTP-ответ; план появляется позже; failed-план ретраится.
- Метрика `bot_tasks_planning_seconds` и алерт на >120 с.

**Приоритет:** высокий (следующий UX-спринт после provider/cost).

## UX: статистика в футере задачи (токены, время, ETA)

**Проблема (2026-11-11, задача #16).** Карточка/сообщение задачи показывает только «шаг 3/1 · попыток 1» и сырой `срок 2026-11-11T00:53:20…`; не видно, сколько токенов/денег уже потрачено, сколько времени идёт задача и когда примерно закончится.

**Ожидаемое поведение.**
- В футере задачи (Telegram status-сообщение и карточка Mini App): `токены: 12.4k→3.1k · ~$0.04 · идёт 6:12 · осталось ~7 мин (шаг 3/3)`.
- Токены/стоимость суммируются по шагам и обновляются после каждого шага; стоимость — по `MODEL_PRICES` и фактической модели.
- ETA: среднее время завершённых шагов × оставшиеся; до первого завершённого шага — «оценка после шага 1» или ETA по историческому среднему; ETA не показывается как точное время, если данных нет.
- Финальный футер: итоговые токены, стоимость, общее время, фактическое завершение.
- Не менять семантику внутренних UTC-полей; отображение — через форматтер времени (см. ниже).

**Критерий готовности.**
- После каждого шага цифры в футере обновляются; нет «сырых» ISO-строк.
- Сумма токенов совпадает с usage по задаче (тест на 3 шага).
- ETA исчезает/помечается «—» при отсутствии данных; тесты на 0/1/много шагов.
- Mini App и Telegram показывают одинаковый набор полей.

**Приоритет:** высокий (следом за асинхронным созданием задачи).

## UX: человекочитаемое время везде

**Проблема.** Пользователь видит `2026-11-11T00:53:20.112588140Z`, `срок 2026-11-11T…`, `истекает 2026-11-11T…`; секунды/наносекунды и UTC не читаются.

**Ожидаемое поведение.**
- Единый форматтер: относительное время для ближайшего (`через 12 мин`, `2 ч 5 мин`, `вчера 18:40`) и абсолютное для дат (`11 ноя, 00:53`), с указанием зоны.
- Убрать ISO/наносекунды из Telegram, Mini App, `/task`, `/remind`, истории, usage-подписей и экспорта; в API оставить ISO (машиночитаемо), форматировать на клиенте/в боте.
- Длительности: `6:12`, `2 ч 5 мин`, не `372.123s`; для ETA — `~7 мин`.
- Локализация RU/EN, корректные склонения; тесты на границы (0, 59 с, 1 мин, 59 мин, 23 ч, вчера/завтра).

**Критерий готовности.**
- Ни один пользовательский экран не показывает `T…Z` и наносекунды.
- Один общий helper используется Telegram и Mini App; snapshot-тесты для RU/EN.
- API-контракты не ломаются (ISO остаётся в JSON).

**Приоритет:** высокий (вместе с футером задачи).

## Настройки: часовой пояс глобально для пользователя

**Проблема.** Всё время отдаётся в UTC/серверной зоне; пользователь в Asia/Yekaterinburg видит сдвиг на 5 часов в задачах, напоминаниях, истории, usage и экспорте.

**Ожидаемое поведение.**
- Настройка `TIMEZONE` (IANA, напр. `Asia/Yekaterinburg`) в Mini App Settings и команда `/timezone`; scope — пользователь (private) / чат (группа), с дефолтом из env `DEFAULT_TIMEZONE` (для текущего владельца — Asia/Yekaterinburg).
- Применяется глобально ко **всему пользовательскому времени**: задачи (создание, срок, ETA, завершение), напоминания, история сообщений, usage-корзины/подписи, `/stats`, `/limits`, экспорт, письма/уведомления.
- Хранение и вычисления остаются в UTC; конвертация только на границе отображения и при вводе времени пользователем (`/remind 18:30` трактуется в его зоне).
- Валидация IANA, DST-корректность; смена зоны не переписывает исторические timestamps, только отображение.
- API: `timezone` в `/api/settings` (current/source) и `PUT /api/settings/timezone`; `GET/PUT /api/admin/...` не нужен, если scope пользовательский; для групп — владелец/админ.

**Критерий готовности.**
- Тест: сообщение с `created_at=2026-11-10T21:00:00Z` отображается как `11 ноя, 02:00` для Asia/Yekaterinburg и `21:00` для UTC.
- DST-переход (Europe/Berlin) не даёт сдвига на час в ETA/напоминаниях.
- Смена зоны влияет на все перечисленные экраны без рестарта; невалидная зона → 400.
- Напоминания, созданные до смены зоны, срабатывают в тот же абсолютный момент UTC.

**Приоритет:** высокий (после футера задачи; можно делать параллельно).


## UI: нечитаемые карточки «Провайдеры и модели»

**Проблема (2026-11-11, скриншот Settings).** В админ-разделе «Провайдеры и модели» карточки провайдеров отрисованы светлым блоком, но подписи/заголовки/подсказки остались очень светлыми (`--muted`/белый текст на белом фоне): имя провайдера, host/source, «Модели (по одной в строке)», «Модель по умолчанию» и подпись чекбокса почти не читаются. Селект обрезает подпись по высоте, у полей нет явного контраста с фоном. На мобильном 320–400px карточки выглядят «выцветшими» и не соответствуют остальному тёмному UI.

**Ожидаемое поведение.**
- Карточки провайдеров используют те же токены темы, что и остальные секции: фон `--card`, текст `--text`, подписи `--muted` с контрастом не ниже WCAG AA (4.5:1) на своём фоне.
- Заголовок провайдера, host, «Источник: env (MODEL_PROVIDERS)», счётчик `N / 20`, label чекбокса и select читаемы на светлой и тёмной теме.
- Select не обрезает значение, textarea имеет min-height и placeholder-контраст; фокус-кольцо видно.
- Карточки не «прыгают» при переключении темы; 320px без горизонтального скролла.

**Критерий готовности.**
- Скриншоты/тест контраста для всех 5 тем (см. ниже), AA для текста и подписей.
- Playwright/JS-тест: у карточки провайдера вычисленный цвет текста и подписей отличается от фона не менее чем на AA; select показывает полный `default_model`.
- Ручная проверка на 320px и 390px: нет обрезки и нечитаемых подписей.

**Приоритет:** высокий (визуальный баг в только что добавленном разделе).

## UX: 5 цветовых тем Mini App (приглушённые, мягкие)

**Проблема.** Сейчас Mini App фактически одна тёмная схема; пользователь не может выбрать комфортную, а новые админ-секции усугубляют контраст.

**Ожидаемое поведение.**
- Настройка `THEME` в Mini App Settings (и, опционально, `/theme` в Telegram для Mini App): **5 схем** с приглушёнными, мягкими цветами, без кислотных акцентов и чистого чёрного/белого. Примеры: `graphite` (текущая мягкая тёмная), `sand` (тёплый светлый), `ocean` (холодный серо-синий), `forest` (приглушённый зелёный), `lavender` (пыльная лаванда).
- Тема задаёт полный набор CSS-переменных: фон/поверхности/карточки, текст/подписи, границы, primary/secondary/accent, success/warning/danger, hover/focus, графики usage (линии/бары/сетка), code/markdown, badges, disabled.
- Применяется глобально ко всему Mini App (все вкладки, админ-секции, модалки, тосты, графики), без перезагрузки; переключение мгновенное.
- Выбор сохраняется: per-user/чат в БД (как language) + localStorage для мгновенного применения до загрузки API; при первом входе — дефолт `graphite` или системная `prefers-color-scheme`.
- Контраст: текст ≥ AA 4.5:1, крупные заголовки ≥ 3:1, focus-visible не теряется; цвет не единственный носитель статуса.
- API: `GET /api/settings` → `theme {current, default, source}`; `PUT /api/settings/theme` strict JSON `{"theme":"ocean"}`; неизвестная тема → 400.
- Telegram-тема не меняется; тема Mini App не влияет на сообщения бота.

**Критерий готовности.**
- 5 тем отрисованы и переключаются без FOUC; после reload и на другом устройстве выбор сохраняется.
- Все существующие экраны (Chat, Tasks, History, Documents, Usage, Settings, admin providers/limits, approval cards, ошибки) читаемы в каждой теме.
- Тест-скрипт контраста для пар «текст/фон» и «подпись/фон» по всем 5 темам; скриншоты 320/390px.
- JS-тесты: переключение, сохранение в API, fallback на default при неизвестной теме, отсутствие inline-стилей/внешних шрифтов.

**Приоритет:** средний-высокий (после исправления текущего UI-бага; можно делать одним спринтом).

## Надёжность: шаг задачи падает по таймауту (~300 с)

**Проблема (2026-11-11, задача #16).** Шаг 3 падает с
`context deadline exceeded: the budget of STRATA_TIMEOUT_SECONDS is spent — the answer is not retried again`
через ~300 с. В конфиге при этом `STRATA_TIMEOUT_SECONDS=240`, `TASK_MODEL_TIMEOUT_SECONDS=300`,
`TASK_STEP_DEADLINE_SECONDS=600`, то есть задача должна иметь собственный бюджет шага, но в ошибке фигурирует
**чатовый** бюджет STRATA. Похоже, дедлайн шага/контекст пробрасывается в модель как `STRATA_TIMEOUT_SECONDS`,
и один длинный вызов (сбор данных/синтез) убивает весь шаг без повтора.

**Ожидаемое поведение.**
- Для task-вызовов бюджет определяется только `TASK_MODEL_TIMEOUT_SECONDS` и `TASK_STEP_DEADLINE_SECONDS`;
  `STRATA_TIMEOUT_SECONDS`/`TG_REPLY_DEADLINE_SECONDS` не должны появляться в ошибке задачи.
- Step deadline ≥ сумма нескольких tool-round’ов + финальный/синтез-вызов; если модель не уложилась —
  шаг повторяется один раз (существующий per-step retry должен срабатывать и на `DeadlineExceeded`), а не
  падает сразу.
- Длинный research-шаг (5+ tool-round’ов, 10–15 мин) доходит до результата или падает с понятной причиной
  «шаг превысил N мин», без технического `STRATA_TIMEOUT_SECONDS`.
- В футере/статусе — человекочитаемые «идёт 5:12 · осталось ~…», а не ISO/сырые секунды.

**Диагностика перед фиксом.**
- Залогировать в момент ошибки: `req.Timeout`, `ctx.Deadline`, `step_started`, `task_model_timeout`,
  `strata_timeout`, номер шага и фазу (tool-round / final / synthesis).
- Проверить, не теряется ли `Request.Timeout` при per-step retry/continuation и не применяется ли
  chat-дедлайн к `runToolLoop`/`synthesizeTask`.

**Критерий готовности.**
- Тест: fake-модель отвечает 350 с (или context с укороченным deadline) → шаг ретраится/завершается,
  ошибка не содержит `STRATA_TIMEOUT_SECONDS`.
- Тест: 5 tool-round’ов укладываются в step deadline; `TASK_MODEL_TIMEOUT` < `TASK_STEP_DEADLINE` соблюдается.
- Живая задача с 3 шагами и веб-поиском завершается; в логах есть реальные бюджеты.
- Метрика `bot_task_step_timeouts_total{phase}` и алерт на рост.

**Приоритет:** критический — задачи с research-шагами сейчас не доживают до конца.
