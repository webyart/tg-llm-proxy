# tg-llm-proxy v1.56.0

## Voice input in the Mini App chat

- The Mini App chat composer has a 44 px mic button with an accessible label and `aria-pressed` while recording. `MediaRecorder` picks the first supported type (`audio/webm;codecs=opus`, then `audio/ogg;codecs=opus`, `audio/ogg`, `audio/mp4`); the recording bar shows elapsed seconds plus Stop and Cancel. Cancel releases the microphone tracks and uploads nothing.
- `POST /api/transcribe` (`multipart/form-data`, one `file` part, bearer session) returns `200 {"text":"…"}`. It reuses the SAME `model.Transcriber`, audio allowlist/signature check, `MEDIA_MAX_MB` and per-minute budget as the Telegram voice handler; there is no second transcription path. Statuses: `400 invalid_body` / `unsupported_audio` / `audio_too_short`, `401`, `405`, `413 body_too_large`, `415 content_type`, `429 rate_limited`, `500 transcription_failed`. The body cap is `MEDIA_MAX_MB` + 64 KiB multipart overhead and the audio is never stored (no message, RAG row or audit detail).
- The transcript is trimmed, inserted into the composer (merged with existing text, bounded to 2000 runes) and focused; it is never auto-sent. RU/EN messages cover permission denied, unsupported browser, too-short recording and network failure.
- Browser support: `MediaRecorder` and `getUserMedia` over HTTPS/localhost. iOS Safari/older WebViews may lack `MediaRecorder`; the button then shows a clear localized message and the user can send the voice note in Telegram.
- Tests: bot dispatcher (shared client request fields, trim, empty transcript, oversize, non-audio/signature mismatch, short audio, allowlist and rate limit), webapp (401/405, missing/wrong field, non-audio, short, 413, 415, 200 with text, backend error → 500, audit, no audio in the DB, mutation rate limit) and Node frontend (start/stop upload and insertion, cancel, permission denied, unsupported browser, too short, network failure).

# tg-llm-proxy v1.52.1

## A Mini App answer survives closing the window

- Closing the Mini App cancels the HTTP request; the generation was bound to that context, so the question was stored, the model call aborted, and no answer row existed (three such questions were visible in the database).
- The work context is now detached from the client (`context.WithoutCancel` plus the same reply/stream budget), delta emission is best-effort, and the assistant row is written as usual. Reopening the Mini App shows the answer in history.
- The network-approval wait deliberately still listens to the client context: a closed window must not keep a pending decision alive, and no network action happens without a decision.
- Test `TestMiniAppAnswerSurvivesAClientDisconnect` cancels the request mid-generation and asserts the stored answer.

# tg-llm-proxy v1.51.2

## Slow document uploads keep their response

- A 8.6 MiB PDF was cut at 5.00 s (408) and a 12-second test upload stored its document but lost the response to the 10-second server write timeout, which Traefik reported as 502 while the row already existed.
- The webapp server now uses `ReadTimeout` 10 minutes and `WriteTimeout` 15 minutes: `ReadHeaderTimeout` (2 s), `MaxBytesReader` and per-route rate limits still bound abuse, while a phone upload plus PDF/DOCX extraction is no longer cut mid-flight. The upload handler keeps its own read/write deadlines and logs a refused extension at debug.
- The edge gateway bounds went to `readTimeout` 600 s and `responseHeaderTimeout` 300 s (commits `78db806`, `164553c`).
- Verified live: a deliberately throttled 410 KB DOCX over 12.6 s through the gateway returned 201 (1 chunk, embedded); the test documents were deleted. The user's three PDFs remained stored.
# tg-llm-proxy v1.51.1

## A document upload gets its own read deadline

- Both of the user's uploads (2.26 MB and 1.18 MB) were cut at exactly 5.00 s and reported as 400: the webapp server-wide `ReadTimeout` is 5 s so JSON endpoints fail fast, and it also applied to a multipart upload from a phone.
- `POST /api/documents` now extends the read deadline to 5 minutes for its own request via `http.ResponseController`; the body cap (20 MiB + 1 MiB overhead) is unchanged. An interrupted transfer returns 408 `upload_timeout` with a localized message instead of a generic body error, and the warning log carries the error and Content-Length.
- The edge gateway's web entrypoint read timeout was raised from 30 s to 300 s (`edge-gateway` commit `b61a4d1`): the old value would have cut a 20 MiB upload from a slow link.

# tg-llm-proxy v1.51.0

## PDF и DOCX в RAG: `/docs add` и Mini App

- Один вход `bot.ExtractDocumentText` для Telegram `/docs add` и `POST /api/documents`: UTF-8 текст (прежняя проверка), PDF через `github.com/ledongthuc/pdf` (MIT, pure Go, без cgo), DOCX через `archive/zip` + `encoding/xml` без новой зависимости. Старый `.doc` отклоняется с подсказкой сохранить как `.docx` или `.pdf`.
- Лимиты: текст — 64 КиБ (`DocumentMaxBytes`), PDF/DOCX — 20 МиБ (`DocumentBinaryMaxBytes`, ровно предел Telegram Bot API `getFile`); `MEDIA_MAX_MB` к документам не применяется. Тело Mini App upload — 20 МиБ + 1 МиБ multipart-overhead. Извлечённый текст нормализуется (UTF-8, без NUL/control, blank-line collapse, trim) и обрезается до `DocumentTextMaxRunes = 200 000` с маркером; chunking/store и best-effort embeddings не менялись.
- Ошибки без записи в базу: скан-only PDF — `no text layer — OCR is not available` (веб `400 document_no_text`, Telegram — понятное сообщение), зашифрованный PDF — `PDF is encrypted; remove the password and retry` (`400 document_encrypted`), битый файл — `400 invalid_document`, `.doc` — `400 unsupported_document`.
- Mini App: `.pdf`/`.docx` в `accept`, pre-check по расширению, затем по лимиту типа (64 КиБ текст / 20 МиБ PDF/DOCX), RU/EN-подсказки называют форматы и 20 МиБ; hint обновлён.
- Тесты: `internal/bot/extract_test.go` (uncompressed PDF, PDF без текстового слоя, DOCX из двух параграфов, `.doc`, NUL/control и truncation, plain text без изменений, per-type limit, ingest scan-only ничего не сохраняет), webapp upload (PDF 1 МиБ → 201 и в чанках извлечённый текст; DOCX → 201; scan-only → 400; PDF > 20 МиБ → 400; 5 МиБ `.txt` → 400; тело > cap → 413; `.doc` → 400), frontend `documents_upload.test.js` (accept, per-type pre-check, 20 МиБ boundary). Docker `go test ./internal/bot ./internal/webapp`, `gofmt`, `go build ./...`, `node --check`, `node --test`.
- Зависимость: `github.com/ledongthuc/pdf v0.0.0-20261020125853-5e46805f718e` (go.sum), других новых модулей нет.

# tg-llm-proxy v1.50.1

## A text document is accepted by its extension when the MIME is vendor-specific

- Only `.txt` uploaded from the Mini App: phones label `.csv` as `application/vnd.ms-excel` and `.md` as `application/x-markdown`, and the validator rejected any non-empty MIME it did not recognise before looking at the extension.
- The extension list is now the explicit contract: a known text extension passes once the bytes are valid UTF-8 without NUL/control characters; binary content is still rejected by those checks. The Mini App pre-check mirrors the same rule, so the picker no longer refuses a file the server would accept.
- Live verification through the real Mini App session: `vendor.csv` with `application/vnd.ms-excel` → 201, `vendor.md` with `application/x-markdown` → 201; binary `.png`/`.exe` stay rejected. PDF and DOCX remain unsupported by design (they are binary formats and need text extraction).
- Tests: `documentIsText` vendor-MIME table and a webapp upload test for both files.
# tg-llm-proxy v1.50.0

## Mini App: загрузка документов в RAG

- `POST /api/documents` принимает `multipart/form-data` с одной частью `file` и необязательным `name`; chat/user берутся только из bearer-сессии. Успех — `201 {"id","name","chunks","embedded"}` без текста документа. Ошибки: `400 document_empty|unsupported_document|document_too_large|invalid_body`, `409 document_limit`, `413 body_too_large` (cap `MEDIA_MAX_MB` + 64 КиБ multipart-overhead), `415 content_type`.
- Валидация и ingest вынесены в общий `bot.IngestRAGDocument`, поэтому Mini App и `/docs add` используют один `documentIsText` (UTF-8, NUL/control, MIME/extension), один лимит 64 КиБ и один вызов `store.PutRAGDocumentWithLimit` с `RAG_MAX_DOCUMENTS`. Эмбеддинги — тот же best-effort `bot.EmbedDocumentChunks`; `embedded` в ответе означает, что все чанки получили вектор.
- Вкладка «Документы»: выбор файла и кнопка «Загрузить» (44 px, mobile-first), клиентский pre-check расширения и размера, состояние «Загрузка…» с блокировкой повторного нажатия, toast и обновление списка; RU/EN, без inline-обработчиков, внешних зависимостей и изменений CSP.
- Проверки: `internal/webapp/documents_upload_test.go` (401, spoofed `chat_id`, 415, пустой/бинарный/oversized текст, 413, 409, 201 с nil/fake/failing embeddings, замена по имени), `internal/webapp/frontendjs/documents_upload.test.js`; Docker `go test ./internal/webapp ./internal/bot`, `go build ./...`, `gofmt`, `node --check`.
