# BACKLOG

Задачи, отложенные по просьбе владельца. Формат: проблема → ожидаемое поведение → критерий готовности.

## UX: создание задачи блокирует интерфейс

**Проблема (2026-11-11).** В Mini App после нажатия «Создать» интерфейс блокируется на всё время генерации плана: `CreateTask` синхронно ждёт ответ STRATA (десятки секунд), кнопка/форма недоступны, прогресса нет. Пользователь видит только «выполняется» уже после создания.

**Ожидаемое поведение.**
- `POST /api/tasks` отвечает быстро: задача создаётся в статусе `planning`, план генерируется фоновой горутиной/воркером.
- UI сразу показывает карточку «План готовится…» с возможностью отменить; форма разблокирована.
- Ошибка планирования переводит задачу в `failed` с понятной причиной и кнопкой «Повторить план», а не молчаливый таймаут.
- Telegram `/task` получает тот же асинхронный путь (не блокирует dispatcher на минуту).

**Критерий готовности.**
- p95 ответа `POST /api/tasks` < 300 мс при живом STRATA.
- UI не блокируется, виден статус `planning` и отмена.
- Тест: медленный fake-модельный клиент (5 с) не задерживает HTTP-ответ; план появляется позже; failed-план ретраится.
- Метрика `bot_tasks_planning_seconds` и алерт на >120 с.

**Приоритет:** высокий (следующий UX-спринт после provider/cost).

## UX: статистика в футере задачи (токены, время, ETA)

**Проблема (2026-11-11, задача #16).** Карточка/сообщение задачи показывает только «шаг 3/1 · попыток 1» и сырой `срок 2026-11-11T00:53:20…`; не видно, сколько токенов/денег уже потрачено, сколько времени идёт задача и когда примерно закончится.

**Ожидаемое поведение.**
- В футере задачи (Telegram status-сообщение и карточка Mini App): `токены: 12.4k→3.1k · ~$0.04 · идёт 6:12 · осталось ~7 мин (шаг 3/3)`.
- Токены/стоимость суммируются по шагам и обновляются после каждого шага; стоимость — по `MODEL_PRICES` и фактической модели.
- ETA: среднее время завершённых шагов × оставшиеся; до первого завершённого шага — «оценка после шага 1» или ETA по историческому среднему; ETA не показывается как точное время, если данных нет.
- Финальный футер: итоговые токены, стоимость, общее время, фактическое завершение.
- Не менять семантику внутренних UTC-полей; отображение — через форматтер времени (см. ниже).

**Критерий готовности.**
- После каждого шага цифры в футере обновляются; нет «сырых» ISO-строк.
- Сумма токенов совпадает с usage по задаче (тест на 3 шага).
- ETA исчезает/помечается «—» при отсутствии данных; тесты на 0/1/много шагов.
- Mini App и Telegram показывают одинаковый набор полей.

**Приоритет:** высокий (следом за асинхронным созданием задачи).

## UX: человекочитаемое время везде

**Проблема.** Пользователь видит `2026-11-11T00:53:20.112588140Z`, `срок 2026-11-11T…`, `истекает 2026-11-11T…`; секунды/наносекунды и UTC не читаются.

**Ожидаемое поведение.**
- Единый форматтер: относительное время для ближайшего (`через 12 мин`, `2 ч 5 мин`, `вчера 18:40`) и абсолютное для дат (`11 ноя, 00:53`), с указанием зоны.
- Убрать ISO/наносекунды из Telegram, Mini App, `/task`, `/remind`, истории, usage-подписей и экспорта; в API оставить ISO (машиночитаемо), форматировать на клиенте/в боте.
- Длительности: `6:12`, `2 ч 5 мин`, не `372.123s`; для ETA — `~7 мин`.
- Локализация RU/EN, корректные склонения; тесты на границы (0, 59 с, 1 мин, 59 мин, 23 ч, вчера/завтра).

**Критерий готовности.**
- Ни один пользовательский экран не показывает `T…Z` и наносекунды.
- Один общий helper используется Telegram и Mini App; snapshot-тесты для RU/EN.
- API-контракты не ломаются (ISO остаётся в JSON).

**Приоритет:** высокий (вместе с футером задачи).

## Настройки: часовой пояс глобально для пользователя

**Проблема.** Всё время отдаётся в UTC/серверной зоне; пользователь в Asia/Yekaterinburg видит сдвиг на 5 часов в задачах, напоминаниях, истории, usage и экспорте.

**Ожидаемое поведение.**
- Настройка `TIMEZONE` (IANA, напр. `Asia/Yekaterinburg`) в Mini App Settings и команда `/timezone`; scope — пользователь (private) / чат (группа), с дефолтом из env `DEFAULT_TIMEZONE` (для текущего владельца — Asia/Yekaterinburg).
- Применяется глобально ко **всему пользовательскому времени**: задачи (создание, срок, ETA, завершение), напоминания, история сообщений, usage-корзины/подписи, `/stats`, `/limits`, экспорт, письма/уведомления.
- Хранение и вычисления остаются в UTC; конвертация только на границе отображения и при вводе времени пользователем (`/remind 18:30` трактуется в его зоне).
- Валидация IANA, DST-корректность; смена зоны не переписывает исторические timestamps, только отображение.
- API: `timezone` в `/api/settings` (current/source) и `PUT /api/settings/timezone`; `GET/PUT /api/admin/...` не нужен, если scope пользовательский; для групп — владелец/админ.

**Критерий готовности.**
- Тест: сообщение с `created_at=2026-11-10T21:00:00Z` отображается как `11 ноя, 02:00` для Asia/Yekaterinburg и `21:00` для UTC.
- DST-переход (Europe/Berlin) не даёт сдвига на час в ETA/напоминаниях.
- Смена зоны влияет на все перечисленные экраны без рестарта; невалидная зона → 400.
- Напоминания, созданные до смены зоны, срабатывают в тот же абсолютный момент UTC.

**Приоритет:** высокий (после футера задачи; можно делать параллельно).
